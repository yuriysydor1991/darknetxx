## Project tests

Project already contains some simple test samples. Based on them you may implement full test of the introduced code. 

Besides the unit and the component tests of separate classes and functions, the project holds the integration tests of the whole executables: the one of the `darknetxx`, which trains a tiny network to recognize the digits and checks its detections (the training of the dxxwjz4p project of the digit images unpacked into the temporary directory into the dxxwjz4 file and the chart beside the project among them), and the one of the conversion command line of the `darknetxx`, which converts the weights files of every generated network back and forth by the [darknetxx-datadrivers](https://github.com/yuriysydor1991/darknetxx-datadrivers) library (the `darknetxxConverter` binary is the one of the library, which tests it). Each comes in two flavors: a GoogleTest one and a bash script one with no test framework (see the [Enabling integration testing](/doc/sections/en_US/5-3-3-enabling-integration-testing.md) section).

The network infrastructure (see the [Darknet adaptor components](/doc/sections/en_US/4-7-2-darknet-adaptor-components.md) section) comes with it's component tests:

- The network weights files formats are the ones of the darknetxx-datadrivers library, which carries the tests of the formats themselves: the documents, the parsers and the codecs of the floats, the validators, the ZIP archives, the cfg sections, the zlib controller and the `darknetxxConverter` binary. The component tests of the [`src/NetworksLoaders/network-weights/tests/component`](/src/NetworksLoaders/network-weights/tests/component) directory cover the formats of the darknet networks: they generate thousands of networks and their weights files (every weights layer kind with the combinations of it's options, every header version, the resolutions from the 2x2 pixels up to the DCI 4K ones, the random networks and the real world sized ones up to the 248 MB of the YOLOv3 weights), save and load them by the readers and the writers of every format of the library through the `NetworkWeights` view of the networks and check the files byte by byte and value by value against the layouts and the JSON documents the tests model independently of the Darknet code and of the library (read by the zlib and the nlohmann json tree parser), the original weights files converted to the documents of every format and back into the same bytes, the projects of the annotations, the YOLO4 folders and the conversion of the files between the formats included.
- `CTEST_NetworkWeights` covers the bridge of the two: the layer types of the library are the darknet ones value for value, the structure of the cfg the library reads the original weights files by (the `CfgNetworkStructure` of the `darknetxxConverter` binary, which knows no darknet code) is the layout of the very same arrays as the darknet network of the cfg (the `NetworkWeights` view of it, the one the `darknetxx` reads the files by) for the saves, the loads, the EMA saves, the transposed loads and the cutoffs of every cfg file of the [misc/examples/cfg](/misc/examples/cfg) directory and of the network loader tests the darknet builds the network of, the arrays of the view are the arrays of the darknet network, and the original weights and the dxxwjz1 files round trip the arrays of the network through the view.
- `CTEST_TrainingJournal` covers the journal of the training: the losses and the mAPs recorded once in the order of the iterations, the time of the resumed training added, the files of the format given; `CTEST_TrainingChart` the chart of the training record: the chart redrawn of the record is the live one pixel by pixel, the chart of the resumed training starts with the whole record and is saved at once; `CTEST_TrainingData` the lists and the labels of the project the darknet C code reads instead of the files and the classes of the boxes the classifier trains; `CTEST_NetworkRewriter` the edited network written into the files of the formats keeping it, of the weights of the unchanged layers.
- `CTEST_OrigDefaultLoader` covers the network cfg parser: the reference networks and their weights, the generated networks of every layer kind checked against their specifications, the memory of the layers (the buffers of the training and the inference networks, the aliased and the shared ones), the cfg errors, the layers of the classifier (the trained `[connected]` one, the classes of the `[softmax]` one) and the networks the loader hands to the `DarknetContext` for the training, the mAP calculation and the detection. The cfg file reader, the `CfgSection` of the darknetxx-datadrivers library, is covered by the tests of the library.
- `CTEST_ALayerAdaptor` and `CTEST_ANetworkAdaptor` cover the memory of the layers and the networks. The latter resizes the networks of every resizable layer kind and the generated ones back and forth and checks the geometry and every buffer size of their layers against the fresh parse of the new size, and the computation of every layer against the fresh network one, value by value. It computes every generated network, fuses the batch normalization without changing the network output and checks the binary weights of the XNOR layers.
- `CTEST_NetworksCApi` covers the Darknet C API implemented by the C++ adaptors, the errors which end the process included.
- `CTEST_BackgroundTrainer` and `CTEST_Yolo4Folder` cover the training of the projects: the YOLO4 folder trained, stopped and resumed, the dxxwjz2p project of the folder trained of it's annotations alone (the lists and the label files removed) up to the mAP of it's validation images, the project updated with the latest weights.

The generated networks and their weights files come from the `DarknetXXWeightsFactory` library of the [`src/tests/component/weights-factory`](/src/tests/component/weights-factory) directory, which the component and the integration tests share. The `DARKNETXX_WEIGHTS_TESTS_SEED` and the `DARKNETXX_WEIGHTS_TESTS_RANDOM_COUNT` environment variables change the seed and the count of the random networks (160 by default), while the `DARKNETXX_WEIGHTS_TESTS_KEEP_DIR` one names the directory to keep the generated cfg, weights and dxxwjz1 files of the tests in, for example:

```
# run from the project build directory

DARKNETXX_WEIGHTS_TESTS_RANDOM_COUNT=5000 ctest -R "CTEST_OrigWeightsFile_random" --output-on-failure
```

The dxxwjz1 families of the biggest networks (the `_resolutions`, the `_big` and the `_random` ones of the dxxwjz1 component tests and of the `ITEST_converter` tests) take tens of minutes in the `Debug` build, since every float of the tens of millions goes through the JSON text, while the `Release` build runs them several times faster.

The memory tests are the most useful in the build of the sanitizers (see the [Enabling sanitizers](/doc/sections/en_US/5-13-enabling-sanitizers.md) section), which reports every access past a buffer the computation of the generated networks makes.

See the [Project build](/doc/sections/en_US/5-project-build.md) subsection to enable unit testing with CMake.
